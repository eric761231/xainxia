## 1. 目標與範圍

優先解決女性人物立繪的身體、衣服非預期透出背景，再檢查整個專案所有實際使用的視覺素材及其渲染流程。驗收不能只看創角，也須涵蓋選角、登入、載入、遊戲場景、地圖編輯器及各平台啟動畫面。

本次「正常透明」包括去背區、抗鋸齒邊缘、細髮、經美術確認的薄紗、光效、陰影、動畫淡出、停用與擺放預覽。不得將所有 PNG 的 Alpha 設成 255，或將所有 Opacity 改成 1。透明登入區與伺服器清單、白字黑描邊是已確認的需求，修正時不得恢復灰黑容器或邊框。

使用者附件 `C:/Users/user/Downloads/1789517163481.jpg` 作為問題外觀參考；JPG 已與背景合成，不能用來還原原始 PNG 的透明通道，也不能僅凭截圖確認根因。

## 3. 第一階段：建立全專案素材與引用清單

### 3.1 清單來源

交叉比對下列資料，而非只搜尋寫死的 `.png` 字串：

1. 全專案圖片檔案：PNG、JPG、WebP、SVG、ICO 及平台解析度變體。
2. `pubspec.yaml` 的資源、字型與啟動畫面宣告；確認子目錄與實際建置打包結果。
3. Dart 的 `Image.asset`、`AssetImage`、`rootBundle`、Flame image cache、Sprite／SpriteSheet、自訂載入器與 fallback。
4. `assets/ui/xaml/assets.xaml`、各 XAML/XML、`character_sprites.json`、`object_catalog.json`、`map_backgrounds.json`、圖集 JSON 與地圖資料。
5. 動態路徑：目錄前綴、`${mapId}.png`、角色／怪物名稱映射、伺服器提供的圖檔名稱及平台條件分支。以執行期載入紀錄補足靜態分析。
6. Web manifest、HTML/CSS、原生資源宣告與 splash 生成設定；字型和程式繪製圖形沒有 PNG Alpha，仍要查其文字／圖形透明度。

### 3.2 交付清單

建立 `docs/asset_alpha_inventory.csv`，每個檔案至少記錄：

`path、sha256、format、width、height、alphaType、alpha0Ratio、alphaPartialRatio、alpha255Ratio、visibleBounds、sourcePath、publishedPath、references、screens、states、usageStatus、expectedTransparency、finding、priority、verificationStatus`。

圖集追加幀／動畫／方向索引與幀內统计。使用狀態分為「已確認使用」「動態待確認」「fallback」「備份／預覽」「未引用」；不得因搜尋不到字串就刪除檔案。所有動態待確認項目都要追到入口或明確記錄缺少的場景條件。

## 4. 第二階段：PNG 透明通道診斷

新增唯讀檢測工具（建議 `tools/assets/audit_alpha.dart`，可沿用既有 `image` 開發相依），輸出統計、Alpha 灰階圖與黑／白／棋盤格／高對比背景合成圖，不覆寫原檔。

檢測內容：

- 解碼驗證、色彩型別、位深、Alpha 通道或調色盤 `tRNS`；區分真正透明與 RGB 畫出的白底／棋盤格。
- 將透明、半透明、不透明像素分別统计，並统计「可見區域內」比例，避免大片去背區干擾判斷。
- 對女性臉部、手臂、身體、實心衣料建立人工確認的主體遮罩；檢查其 Alpha 與 RGB。不能僅凭全圖半透明比例或「像素接近白色」判定錯誤。
- 分開檢查薄紗、髮絲、邊缘抗鋸齒、陰影和光效；對疑似內部破洞使用連通區和合成圖提示，再人工判讀。
- 檢查半透明邊缘的白／黑底污染、預乘 Alpha 處理、縮放取樣暈邊。Alpha 圖正常但仍發白時，追查 RGB 與匯出流程。
- 圖集逐幀檢查：局部異常、相鄰幀滲色、裁切、縮放、方向和動畫切換；不得因單幀正常就判整張圖集通過。

全圖统计只能產生待查警示，不能直接決定修復。背景預期完全不透明與否也須按用途判定，地磚外角等合法透明區不能填滿。

## 5. 第三階段：畫面透明度與混合流程追蹤

為每個實際使用素材建立「來源檔 → 解碼／快取 → 裁切／縮放 → 元件本體 → 父層 → 混合／遮罩 → 最終畫面」記錄。

檢查 `Opacity`、`AnimatedOpacity`、FadeTransition、OpacityEffect、Paint alpha、ARGB 色票、`withValues(alpha:)`、`ColorFiltered`、`ShaderMask`、`saveLayer`、BlendMode、自訂 shader 與祖先元件。XML/XAML/JSON 和 Dart 預設值、平台分支也要納入。

普通 src-over 流程中，素材 Alpha 與多層透明度會相乘；其他 BlendMode／濾鏡須按實際合成順序驗證，不能套同一公式推定。

| 使用區域 | 必查情境 |
| --- | --- |
| 創角／選角 | 男女切換、角色切換、重進畫面、背景蒙版層級、正常／載入狀態 |
| 登入／伺服器 | 容器保持透明、選單展開／收合、可選／維修、白字黑描邊 |
| 載入／過場／訊息 | 進出動畫、光效、遮罩範圍，過場結束後不得殘留人物透明度 |
| HUD 與各面板 | 背包、修煉、社交、布置、GM、提示、圖示與文字的正常／停用狀態 |
| 玩家／遠端玩家／怪物 | 全方向及動作、死亡與重生、淡出重設、陰影和本體分離 |
| 地圖／物件／編輯器 | 地圖背景、地磚拼接、選取、擺放 ghost、取消／完成後本體恢復 |
| 法器／特效 | 逐幀播放、發光、粒子與混合模式；不把光暈變成實心塊 |
| 平台啟動與圖示 | Web／Android／iOS／Windows 實際使用檔及生成來源一致 |

普通主體正常狀態以不施加額外衰減為原則；需要透明的狀態明確命名、指定作用範圍與恢復時機。若只是壓暗背景，蒙版留在背景與人物之間，不包住整個畫面。

## 6. 第四階段：依根因修正

### P0：女性立繪

1. 保存原檔、發布副本及雜湊，確認兩者是否一致；建立與附件同場景的修前對照。
2. 若主體 Alpha 過低且 RGB 細節完整，只在確認的主體遮罩內恢復不透明度，保留背景、髮絲及薄紗過渡。
3. 若去背已破壞 RGB 或主體被誤挖空，回到原始高品質圖重新去背／匯出。不能以硬拉 Alpha 或全圖增亮掩蓋，也不能把使用者 JPG 的背景一起填入人物。
4. 若根因在父層／狀態／混合設定，修正對應作用範圍或重設流程，不重複修改正常 PNG。
5. 創角和選角共同驗證，男角作為對照，確保同一份資源修正沒有只生效在一頁。

### P1：其他已使用素材與共用流程

依清單處理玩家、怪物、物件、地磚、UI、法器；每項分類為「素材錯誤」「渲染錯誤」「正常透明」「需美術判讀」，附修前後證據。修共用載入器／繪製器時，驗證所有呼叫者，不只目前可見畫面。

### P2：發布一致性與防回歸

- 原始素材與內容版本檔由同一發布步驟產生；修圖後重新计算雜湊、更新引用和預載清單，避免手動維護兩份不同圖片。
- 重新打包並比對 bundle 內的檔案雜湊；禁止只替換 `build` 內某張 PNG 作為正式修復。
- 確認實際網頁網址、靜態服務目錄、部署版本、HTTP 快取及 service worker；使用新瀏覽器工作階段和既有工作階段各測一次。
- 清快取只作診斷／更新驗證，不列為像素透明問題的修復方式。

## 7. 驗收與回歸測試

### 素材驗收

- 人物臉、手、身體及確認為實心的衣料不透出背景；經確認應不透明的內部測試遮罩，在 8-bit Alpha 下應為 255。邊缘及薄紗另設預期，不套主體門檻。
- 去背背景維持透明，邊缘平滑，沒有白框、黑邊、硬切髮絲或整片實心薄紗。
- 每份已使用素材都有分類結果與證據；無法重現／待美術確認者明列，不能標成通過。

### 畫面驗收

- 在黑、白、棋盤格及實際遊戲背景上比較修前後；女性全身與臉／手／裙裝局部都要留圖。
- Web 優先，以 1920×1080、1280×720 及實際問題視窗驗證；覆蓋正常、切換、過場、停用與恢復狀態。
- 加入有判別力的素材遮罩測試、共同立繪元件渲染測試及狀態恢復測試；圖集按幀／方向抽查之外，工具統計須遍歷全部幀。
- Shader、圖集與取樣差異在可用的原生平台補驗；無裝置的平台如實記錄未驗，不以編譯成功代替視覺驗證。
- 保留現有登入與選服測試，確認透明容器和帳密保留功能沒有回歸。
